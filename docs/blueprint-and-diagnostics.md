## Which principles are most beneficial

Start every project with the quality-safe foundation: **256-aligned per-device dimensions ([Principle 1](shape-rules.md#1-align-every-per-device-reduction-and-output-dimension-to-256))**, **static shapes with `SMEM` scalar-prefetch dropless routing ([Principle 3](shape-rules.md#3-static-and-dynamic-shapes))**, **one parallelism plan mapped onto physical links ([Principles 2](shape-rules.md#2-plan-one-parallelism-strategy-from-4-chips-to-multi-pod) and [10](systems-mapping.md#10-map-model-axes-onto-the-physical-mesh))**, **wall-clock ablations on a tuned baseline ([Appendix A.6](appendix-a.md#a6-measure-ablations-in-wall-clock-not-flops))**, and **published reference targets to judge the result ([Appendix A.8](appendix-a.md#a8-reference-performance-targets))**. Together these cover the largest measured efficiency gaps with near-zero model-quality risk.

For any MoE architecture, add **[LatentMoE](architecture-choices.md#4-compress-routed-token-traffic-with-latentmoe) (Principle 4)** after a validation ablation: it cuts the routing and dispatch traffic that dominates MoE training steps and shrinks the expert weight reads that bound low-batch decode. Beyond that foundation, prioritize by bottleneck regime:

| Bottleneck regime | Reach first for | Why |
| :--- | :--- | :--- |
| **High expert count (> 100 experts)** | Principles [4](architecture-choices.md#4-compress-routed-token-traffic-with-latentmoe), [5](architecture-choices.md#5-raise-compute-intensity-with-a-large-shared-expert-and-wider-experts), [9](architecture-choices.md#9-minimize-exposed-vpu-time), [10](systems-mapping.md#10-map-model-axes-onto-the-physical-mesh) | Routing and dispatch dominate step time: compress the routed token path (`LatentMoE` + FP8 dispatch), pair every LatentMoE layer with a large shared expert, trade excessive `(N, K)` fragmentation for wider `d_ff` so per-expert GEMMs fill MXU tiles, offload dispatch sorts/gathers to SparseCore, and keep EP on one short torus axis. |
| **Long context (> 64K)** | Principles [7](architecture-choices.md#7-hybrid-attention-for-long-context-pick-the-tpu-mature-variant), [11](systems-mapping.md#11-tune-the-memory-pipeline) ([App. A.3](appendix-a.md#a3-remat-friendly-blocks)), [1](shape-rules.md#1-align-every-per-device-reduction-and-output-dimension-to-256), [10](systems-mapping.md#10-map-model-axes-onto-the-physical-mesh), [13](systems-mapping.md#13-use-multi-pass-bf16-for-high-precision-bound-compute) | Quadratic attention FLOPs and activation memory dominate: hybrid local/global or linear attention is the primary structural lever and selective rematerialization is second; `head_dim = 256` gains widen sharply with sequence length, load-balanced CP governs exposed collectives, and multi-pass BF16 accelerates BF16-sensitive attention on supported hardware. |
| **Multi-pod scale (> ~100B)** | Principles [2](shape-rules.md#2-plan-one-parallelism-strategy-from-4-chips-to-multi-pod), [10](systems-mapping.md#10-map-model-axes-onto-the-physical-mesh), [4](architecture-choices.md#4-compress-routed-token-traffic-with-latentmoe), [6](architecture-choices.md#6-low-precision-as-architecture-not-afterthought), [8](architecture-choices.md#8-overcome-the-decode-bandwidth-wall-low-diameter-scale-out-81-and-speculative-decoding-82), [12](systems-mapping.md#12-co-design-for-prefilldecode-disaggregation-and-align-with-the-tpu-serving-stack) | Inter-chip and cross-pod communication become the binding constraint: restrict DCN to DP or PP, verify EP viability via roofline arithmetic, bake in range-bounded block-scaled FP8 as matmul share rises, and size serving concurrency and disaggregation upfront rather than retrofitting them. |
| **Latency & goodput serving** | Principles [8](architecture-choices.md#8-overcome-the-decode-bandwidth-wall-low-diameter-scale-out-81-and-speculative-decoding-82), [12](systems-mapping.md#12-co-design-for-prefilldecode-disaggregation-and-align-with-the-tpu-serving-stack), [10](systems-mapping.md#10-map-model-axes-onto-the-physical-mesh), [App. A.4](appendix-a.md#a4-size-the-model-to-your-real-serving-concurrency), [App. A.7](appendix-a.md#a7-quantize-further-for-serving), [7](architecture-choices.md#7-hybrid-attention-for-long-context-pick-the-tpu-mature-variant) | At low concurrency, decode is bound by HBM weight reads and sequential layer count: size active bytes to real serving concurrency, scale out over low-diameter topologies (Boardfly) or wider decode TP, add MTP speculative decoding, and apply 4-bit/FP8 PTQ. At high concurrency or long context, shrink KV cache bytes via hybrid attention and FP8 KV. |

Treat these regime labels as practical entry points rather than rigid cutoffs; use the diagnostic checks below to identify your actual bottleneck from a live trace.

## Diagnosing your own runs

Every principle in this guide maps to observable signals in standard open-source profiling tools (`jax.profiler`, enabled in open-source [MaxText](https://github.com/AI-Hypercomputer/maxtext) with `profiler=xplane`). Open a captured profile in the [XProf / TensorBoard profiler](https://openxla.org/xprof) and inspect six numbers:

| # | XProf signal (`profiler=xplane`) | Healthy range | Action if off-target |
| :--- | :--- | :--- | :--- |
| 1 | **Exposed (un-overlapped) communication share** | A few % of step | Try **overlap first**: latency-hiding scheduler + SparseCore collective offload flags ([Principle 10](systems-mapping.md#10-map-model-axes-onto-the-physical-mesh)). If still exposed, compute per byte transferred sits below the physical link's arithmetic-intensity ridge and no schedule can hide it; reduce communication bytes via sharding changes or LatentMoE + FP8 compression ([Principles 4](architecture-choices.md#4-compress-routed-token-traffic-with-latentmoe), [10](systems-mapping.md#10-map-model-axes-onto-the-physical-mesh)). |
| 2 | **Backward : forward wall-clock ratio** | ≈ 2 (no remat) to ≈ 3 (full remat) | Anything in the 2–3 band reflects an intentional compute-for-HBM trade. Act when the ratio exceeds what HBM pressure requires: checkpoint more projections (`save_qkv_proj`, `save_out_proj`) or shard weights further ([Principle 11](systems-mapping.md#11-tune-the-memory-pipeline)). Ratios above ~4 point to exposed backward collectives or unoptimized backward kernels. |
| 3 | **Large GEMMs (% of chip peak FLOP/s)** | 80–95% | Large dense and grouped matmuls should individually run near MXU peak; lower utilization indicates MXU tile padding from dimensions not divisible by 256 ([Principle 1](shape-rules.md#1-align-every-per-device-reduction-and-output-dimension-to-256)) or suboptimal kernel block sizes (`tune-jax`, [Principle 11](systems-mapping.md#11-tune-the-memory-pipeline)). |
| 4 | **Non-matmul share of step time** | < ~15% dense; < ~30% MoE | Above these bands, standalone elementwise VPU fusions, fine-grained FP8 block rescales, or MoE routing ops (`sort`, `argmax`/one-hot, `cumsum`, `gather`/`scatter`) are eating the step. Fuse RMSNorm/SwiGLU and size FP8 blocks to the MXU window ([Principle 9](architecture-choices.md#9-minimize-exposed-vpu-time)), compress routed tokens ([Principle 4](architecture-choices.md#4-compress-routed-token-traffic-with-latentmoe)), widen experts ([Principle 5](architecture-choices.md#5-raise-compute-intensity-with-a-large-shared-expert-and-wider-experts)), and offload dispatch. |
| 5 | **Engine executing sorts, gathers, and scatters** | SparseCore (in tuned configs) | If routing data movement runs on the TensorCore, SparseCore offload flags are disabled or changed across runtime versions ([Principle 10](systems-mapping.md#10-map-model-axes-onto-the-physical-mesh)). Enable offload and verify the step-time reduction (typically 15–22%) with a short profile. |
| 6 | **Step-time variance after warmup** | Steady, near-zero jitter | Compiled TPU programs are deterministic, so identical shapes execute in identical device time; step-to-step jitter points outside the accelerator to host CPU or data-loading stalls. |

These ranges are triage thresholds rather than universal constants. Achievable utilization depends on model size and sharding: small models will not reach a flagship model's GEMM peak share, and high-communication shardings carry a higher floor. Compare your run against a tuned reference of similar scale ([Appendix A.8](appendix-a.md#a8-reference-performance-targets)), and separate **execution gaps** (fixable via compiler flags and kernel block tuning) from **design gaps** (fixable only by changing model shapes, routing compression, or mesh sharding).

**Roofline a kernel before tuning it.** While the table above triages the full step, channel roofline arithmetic establishes what speed is physically achievable for an individual kernel or collective. Arithmetic intensity equals FLOPs divided by bytes transferred across the feeding channel (HBM for an on-chip kernel, ICI or DCN for a collective), bounding achievable throughput at $\min(\text{Intensity} \times \text{Bandwidth}, \text{Peak Compute})$. Judge each op's measured FLOP/s against *that* roofline ceiling rather than raw chip peak: a memory-bound op sitting at its HBM ceiling cannot be accelerated by tile search, and only gets faster by moving fewer bytes (fusion, lower precision, smaller KV or latent widths). [`jax.experimental.roofline`](https://github.com/jax-ml/jax/tree/main/jax/experimental/roofline) computes static FLOPs and bytes per JAX function.

**Budget HBM before sweeping.** Total HBM usage splits into fixed state and batch-scaling activations. Fixed state (weights, gradients, and Adam optimizer moments: ≈ 16 bytes/parameter at standard mixed-precision defaults) divides across every weight-sharding axis (FSDP, TP, EP, PP), whereas plain DP replicates it. Activations scale linearly with `per-device batch × sequence length` (plus quadratic terms if attention is un-flashed). When a configuration runs out of HBM, apply memory levers in decreasing performance order:

1. Shard weights further (increase FSDP or EP degree within the slice).
2. Adjust activation rematerialization (`custom`, `save_qkv_proj`, `save_out_proj` before `full`).
3. Reduce per-device microbatch size.
4. Enable host memory offload (`parameter_memory_host_offload`, `optimizer_memory_host_offload`) last, as PCIe offload typically costs throughput ([Appendix A.3](appendix-a.md#a3-remat-friendly-blocks)).

**Run optimization as a disciplined program.** Modify one knob per run; 20–30 steps after compilation warmup is sufficient to measure steady-state step time. Capture a fresh XProf trace after every change to confirm the *physical mechanism* (for example, verifying that remat recomputations disappeared or that dispatch gathers moved onto SparseCore), not just the aggregate step time. Record negative experiments alongside wins so settled questions are never re-run, and gate every systems or kernel optimization on a fixed-seed loss-parity check against your baseline.

## Putting it together: ~100B Ironwood LatentMoE

The reference configuration below combines the shape, architecture, and systems principles into a concrete ~100B-total (~17.5B-active) LatentMoE blueprint for TPU v7x (Ironwood):

### Reference config

| Component | Reference choice | Why it fits TPU |
| :--- | :--- | :--- |
| **Backbone** | `d_model = 6144` ($24 \times 256$), `48` uniform LatentMoE layers | Exact 256×256 MXU alignment; uniform layers simplify `jax.lax.scan` compilation and divide cleanly across PP degrees (`2, 4, 6, 8, 12, 16`) and eight `5:1` attention cycles ([Principles 1](shape-rules.md#1-align-every-per-device-reduction-and-output-dimension-to-256), [2](shape-rules.md#2-plan-one-parallelism-strategy-from-4-chips-to-multi-pod), [10](systems-mapping.md#10-map-model-axes-onto-the-physical-mesh), [App. A.1–A.2](appendix-a.md#a1-stay-in-the-conventional-aspect-ratio-band-explore-wider-not-deeper-within-it-via-ladder-ablations)). |
| **Attention & KV** | `head_dim = 256`, 24 Q / 4 KV heads (`QK-norm`); 5:1 sliding-window (`512` or `1,024`, Splash-aligned) : global (`NoPE`); FP8 KV cache (or MLA-style 512-dim latent) | Full MXU tile utilization; bounded long-context prefill FLOPs and decode KV bytes; length extrapolation on global layers ([Principles 1](shape-rules.md#1-align-every-per-device-reduction-and-output-dimension-to-256), [6](architecture-choices.md#6-low-precision-as-architecture-not-afterthought), [7](architecture-choices.md#7-hybrid-attention-for-long-context-pick-the-tpu-mature-variant)). |
| **Shared expert** | 1 large shared expert (`d_shared = 8192` at full `d_model`) in all 48 layers | Dense, communication-free, FSDP-shardable MXU GEMMs overlap EP dispatch/combine, stabilize early routing, and amortize across every decode token ([Principles 4](architecture-choices.md#4-compress-routed-token-traffic-with-latentmoe), [5](architecture-choices.md#5-raise-compute-intensity-with-a-large-shared-expert-and-wider-experts)). |
| **Routed LatentMoE** | 64 routed experts, top-4, `ℓ = 2048` ($3\times$ compression), expert `d_ff = 4096`, FP8 all-to-all dispatch, full-`d` router | Fewer, wider experts yield well-filled grouped GEMMs while $3\times$ latent + $2\times$ FP8 compression cuts cross-chip dispatch bytes $6\times$ ([Principles 4](architecture-choices.md#4-compress-routed-token-traffic-with-latentmoe), [5](architecture-choices.md#5-raise-compute-intensity-with-a-large-shared-expert-and-wider-experts)). |
| **MTP drafter** | 1–2 BF16 draft heads | Denser pretraining supervision signal plus built-in speculative drafter to verify multiple tokens per decode weight read ([Principle 8.2](architecture-choices.md#82-speculative-decoding-as-a-design-input-mtp-heads-or-drafter)). |
| **Precision** | FP8 (E4M3/E5M2, block size ≥ 512 on v7x) for GEMMs; BF16/FP32 router, norms, softmax inputs, embeddings, and final layers | 2× MXU compute throughput over BF16 with range-bounded numerical stability and hidden VPU block rescales; ready for 4-bit serving PTQ ([Principles 6](architecture-choices.md#6-low-precision-as-architecture-not-afterthought), [9](architecture-choices.md#9-minimize-exposed-vpu-time), [13](systems-mapping.md#13-use-multi-pass-bf16-for-high-precision-bound-compute), [App. A.7](appendix-a.md#a7-quantize-further-for-serving)). |
| **Training mesh** | `FSDP × EP8` (1D torus axis) `× TP2` (D2D chiplets); SparseCore offload; zero-init attention outputs; global-batch load balancing; dropless `Megablox` | Parallelism hierarchy matched to physical link bandwidths (`D2D → ICI`); async collectives and dispatch gathers overlapped on SparseCore ([Principles 3](shape-rules.md#3-static-and-dynamic-shapes), [10](systems-mapping.md#10-map-model-axes-onto-the-physical-mesh)). |
| **Serving stack** | Disaggregated prefill and decode pools; FP8 weights and FP8 KV (`block-size = 256`); decoupled attention DP + expert EP | Separates TTFT and TPOT operating points and reaches the ~300-token/shard decode roofline via sparsity + MTP ([Principles 8](architecture-choices.md#8-overcome-the-decode-bandwidth-wall-low-diameter-scale-out-81-and-speculative-decoding-82), [10](systems-mapping.md#10-map-model-axes-onto-the-physical-mesh), [12](systems-mapping.md#12-co-design-for-prefilldecode-disaggregation-and-align-with-the-tpu-serving-stack)). |
